# Rebind - Product and Technical Specification

**Status:** Product specification; implementation and hardware support must be independently verified.  
**Platform:** macOS only, initial target macOS 26+.  
**Product:** Rebind, a lightweight, capable, native input remapper inspired by the useful parts of BetterTouchTool.  
**Companion files:** [AGENTS](../AGENTS.md), [STATE](STATE.md), [WORKFLOW](WORKFLOW.md), [PLAN](PLAN.md), [DESIGN](DESIGN.md). Requirements live here; implementation/evidence and recent changes live in STATE, task records and [CAPABILITIES](CAPABILITIES.md), not in the presence of a requirement.

**Design source:** Current Rebind designs in Sketch, indexed in DESIGN and inspected through MCP before designing or implementing screens. A PNG reference is not required.

## 1. Product vision

Build a **real** desktop utility that lets people map supported physical input to keyboard shortcuts or native macOS actions. It must run in the background with minimal overhead, look like a polished first-party macOS app, and avoid the complexity of a full automation suite.

Example user intent:

- Four-finger trackpad tap → `Command + W`.
- `Control + Mouse Button 4` → next desktop / Space.
- Mouse Button 5 → Mission Control.
- `Option + Mouse Button 4` → `Command + Shift + T`.
- Hold a side mouse button and move left → previous desktop.
- `Control` + wheel up → increase volume.
- Magic Mouse gesture → a chosen shortcut or system action.

**Primary test of success:** after configuration, an input reliably triggers its assigned effect in normal apps without unexpected original input or accidental extra actions. Attractive screens alone are not success.

### Scope and priority conventions

- **Core**: essential to the product; must work in supported contexts to claim general readiness.
- **Research-gated**: essential aspiration but constrained by hardware, OS ownership, driver behavior, private frameworks, or permission semantics. Test and report the supported subset honestly.
- **Later**: useful enhancement only after the core is robust.

Do not quietly delete research-gated requirements. Create a documented capability decision and a visible explanation if a requested interaction is unavailable on the tested configuration.

### Non-goals

Not a Mac App Store product, cross-platform app, macro timeline editor, scripting IDE, cloud sync, analytics collector, or workspace automation tool. Simple named rule profiles with manual selection are supported; no automatic device/app/workspace activation of profiles (a single rule may be limited to one app, §2) or extra profile/workflow/action sidebars. Do not build a companion driver/kernel extension without proof it is necessary, approved, safe, and sustainable.

## 2. Trigger → rule → action contract (CORE)

A binding consists of:

1. **Scope**: input category within the manually selected profile.
2. **Trigger**: key, shortcut, mouse button, click count, hold, scroll, pointer gesture, or multitouch gesture.
3. **Modifiers**: zero or more concurrently held `Command`, `Control`, `Option` and `Shift`. Left/right distinction, Caps Lock and Fn/Globe triggers are outside the current scope.
4. **Action**: supported macOS action, synthetic input, application operation, shortcut, etc.
5. **Settings**: enabled state, gesture timing/thresholds, optional action parameters, stable binding ID.

The same physical input with and without a modifier is a different trigger. Modifiers pressed in any order before the triggering event must match.

Examples:

```text
Profile: G603
Scope: All mice
Trigger: mouse button 4, down
Modifiers: Control
Action: Next Desktop
```

```text
Scope: All trackpads
Trigger: four-finger tap
Modifiers: None
Action: Send Command+W
```

```text
Scope: All mice
Trigger: while mouse button 4 is held, move pointer to the left
Modifiers: None
Action: Previous Desktop
```

### Rules and resolution

- Match exact modifier sets by default, not implicit subsets. If wildcard matching is introduced, expose it explicitly and define priority.
- Only the selected profile participates in matching. Reject equally matching enabled rules within a profile; matching triggers in different profiles are allowed. No physical-device priority or source attribution for rules; mouse-settings attribution is separate.
- Normal passthrough for unmatched input. Suppress a matched original event only when the capture API permits it, and document what is not suppressible.
- Maintain press/release symmetry for synthetic and suppressed events to avoid stuck keys/buttons.
- Ignore tagged synthetic input generated by Rebind (not by blanket suppression of legitimate hardware events).
- Repeats, rapid double taps, long holds, cancellations, and missed release events need deterministic state-machine behavior.
- Prevent a gesture firing repeatedly from each touch frame; one recognized gesture produces the configured number of actions (normally one).
- Avoid double-triggering when both HID and Quartz deliver representations of the same physical input.
- Support a global pause switch and emergency bypass that restores normal input safely.
- **Held output (2026-10-13):** a press rule on a key or mouse button may keep its output for as long as the trigger is held. A shortcut is one key-down, repeats at the system key-repeat rate and one key-up; volume, brightness and scroll actions repeat instead. Every interruption (pause, editing, Secure Input, lost capture, sleep or lock, an excluded app coming to the front, quitting) releases a held key. A button that also carries pointer gestures cannot hold an output.
- **Modifier actions and short press (2026-10-13):** a key or mouse button may act as Command, Option, Control or Shift while held: Rebind posts the modifier press and release and adds the flag to the input it passes on. Rebind's own bindings do not match on it. A hold rule may also carry a shortcut that is sent when the trigger is released before the hold time; this is the supported form of a dual-role key.
- **Excluded apps (2026-10-13):** the user may list apps in which Rebind leaves keyboard, mouse and trackpad input untouched while they are in front. This is a global list, not automatic profile activation, which stays out of scope.
- **Rules for one app (2026-10-15):** a rule may be limited to one app. It works only while that app is in front and there replaces a rule for all apps with the same trigger; two rules for the same app and trigger conflict, and so do a hold/double press and gestures on the same button in an app's effective set.
- Keep rule evaluation synchronous, fast, and allocation-light on the event path; hand off slow action execution outside the hook.

### Suggested compact model (illustrative, not mandated)

```swift
struct Binding: Codable, Identifiable {
    let id: UUID
    var scope: DeviceScope
    var trigger: InputTrigger
    var modifiers: ModifierSet
    var action: RebindAction
    var isEnabled: Bool
}
```

Use associated-value enums or similarly clear models for trigger and action variants. Keep persistence versioned so new trigger kinds can be added without data loss. **Do not** use a five-case mouse button enum. Button identifiers should be represented as numeric HID usage/button numbers with source metadata as appropriate.

## 3. Input categories and capabilities

### 3.1 Keyboard (CORE)

- Built-in, USB, Bluetooth, third-party keyboards.
- Individual physical keys and combinations; record combinations interactively.
- `Command`, `Control`, `Option` and `Shift`; left/right distinction and Fn/Globe are outside the current scope.
- Function keys and standard navigation/editing keys. Caps Lock remapping is outside the current scope.
- Key down/up; hold; double press; repeat awareness; no accidental modifier stickiness.
- Handle keyboard layout changes: persist physical key codes for physical triggers and render human-readable labels based on current layout; distinguish physical key mapping from character insertion.
- Explicitly evaluate Secure Input/password fields and protected OS contexts. Do not promise interception when macOS prohibits it.

**Acceptance K1:** The app can record `Control + Option + [physical key]`, save it, react globally where permitted, and restore it after relaunch.  
**Acceptance K2:** A mapped key does not leak an unintended source event when suppression is supported, and never becomes stuck after pause/restart.

### 3.2 Standard, gaming, and multi-button mice (CORE)

- USB and Bluetooth mice from various vendors, including Logitech G603, MX Master, G502, and compatible alternatives.
- Middle/X/additional buttons at all indices actually surfaced by the OS; vertical/horizontal wheel; mouse-button hold and double press. Primary/secondary buttons as triggers and native triple-click recognition are outside the current scope; primary/secondary click output remains supported.
- Keyboard modifiers + any supported mouse button; combinations of mouse buttons only if safely captured.
- A button that carries pointer gestures still clicks: released without movement, it runs its plain press rule or, without one, its ordinary click (middle, fourth and fifth buttons); the click is delivered on release (2026-10-13).
- Button-hold + pointer movement in exactly four directions: left, right, up and down. This is the complete intended set for mouse pointer gestures; diagonal, circular/spiral and multi-stroke shapes are out of scope (user decision 2026-10-08). Ambiguous movement cancels rather than selecting an unintended direction. Ensure no repeated firing and avoid accidental dragging/click-through. This decision does not change the separate multitouch requirements.
- Modifier + vertical/horizontal scroll mapping; define sensible units and throttling for continuous wheel input. A scroll event without a gesture or momentum phase is a mouse wheel, also when macOS delivers a high-resolution wheel as continuous scrolling; trackpad and Magic Mouse scrolling always carries a phase and is never treated as a wheel (2026-10-15).
- Smooth scrolling (2026-10-15): optional and set per mouse in Settings → Devices; turns each wheel click into a short glide of continuous scrolling, with an adjustable distance per click (slider, default 50 points per line, subsequent user choice in INPUT-011) and a glide length (Short / Standard / Long). A wheel event is attributed to its mouse through the HID service that sent it. Vertical and horizontal reverse are separate global switches in Input.
- Battery in the Menu Bar menu (2026-10-15, on by default): a "Battery" section lists connected Logitech mice and keyboards (HID++) and devices macOS reports, each with its charge.
- Gaming mice with onboard profiles are managed by G HUB while it runs; Rebind then leaves their hardware settings alone (2026-10-15).
- Logitech extras (2026-10-15): battery charge, the high-resolution wheel switch, and the gesture button as a trigger ("Gesture button", alone or with a direction) once enabled for that mouse; Rebind diverts it over HID++ and gives it back when it quits. Wheel bindings act on the original click; Command, Control and Shift clicks and trackpad/Magic Mouse scrolling are never smoothed. Excluded apps can switch bindings and smooth scrolling off separately; smooth scrolling follows the app under the pointer, which receives the scroll, and bindings follow the app in front.
- Button-hold + wheel step (2026-10-13): while a middle or extra button is held, each discrete wheel step in a configured direction runs its rule, with the same throttling. Using the wheel means the hold is not a click or a pointer gesture.
- Interactive **Record Mouse Button** UI. Never require users to type button codes.
- **Do not hard-code 5, 8, or 12 as a maximum.** Record numeric button identifiers actually delivered by Quartz. A model table is not evidence of remappable button counts; claim a hardware button only after its events are observed.
- Note that OEM utilities, onboard profiles, virtual keyboards, and vendor drivers may convert a 'mouse button' into some other event or consume it entirely.
- Device names and inventory (2026-10-15): Settings → Devices lists external mice, keyboards and trackpads across vendors, including devices with no readable battery. Battery reads use driver-provided macOS data, standard HID Battery Strength, existing Logitech HID++, optional standard Bluetooth Battery Service, and known Razer/SteelSeries USB profiles (2026-10-16). Headsets and unclassified accessories are excluded from this tab, even when macOS reports their battery (2026-10-16). A local name (up to 60 characters) replaces the factory name in Devices and the battery menu; clearing it restores the original. Names persist/export with the full configuration, use vendor/model identity (identical models share a name), and never change hardware identity, rules or device settings. Keyboard cards show identity and charge when available, without mouse controls. Only Logitech locations with a mouse/keyboard HID usage and a vendor output interface may open a HID++ session; vendor-only headset interfaces are skipped. Unknown/non-input HID++ device types stop before battery or mouse-feature queries. Other vendors are never actively probed with HID++.
- Multi-vendor battery limits (2026-10-16): proprietary USB queries require a known mouse product and matching control interface; never guess commands from the vendor alone. Bluetooth access is requested explicitly in Devices and used only for already-connected HID-service peripherals, whose static Report Map must identify a mouse, keyboard or trackpad before Battery Level is read. No nearby-device scan, pairing, key-report collection or device settings write. Missing/invalid replies remain unknown; input cards and normal rules still work. Battery protocol implementation is distinct from named-model/transport hardware verification.
- Mouse hardware settings (2026-10-15): Settings → Devices lists connected mice. A Logitech HID++ 2.0 mouse (Bluetooth, USB or a Bolt/Unifying receiver) shows only the settings it reports: SmartShift wheel mode (SmartShift, always click, always free spin) with its sensitivity, and pointer resolution (DPI) from the mouse's own list. Rebind stores the values per model and writes them whenever the mouse is found. Other mice show that they have no extra settings. The Menu Bar menu also has a "Pointer speed" section with a DPI slider for each connected mouse that reports DPI, sharing the stored value with Settings (user request 2026-10-16).
- Companion apps (2026-10-15): while a vendor app that drives mice directly runs (verified identifiers only: Logi Options+, Logitech G HUB), the Mouse page shows one warning naming it ("… is running": it can take over mouse buttons and settings; if something doesn't work, turn it off or uninstall it). Devices shows the same warning only for an app that rewrites these settings (Logi Options+) and disables the settings while it runs; Rebind does not offer to quit it, because it relaunches itself (user report). The gesture button follows the explicit per-mouse enable/diversion contract above; thumb-wheel-specific HID++ diversion remains a later engine task.
- Numbering shown in UI must be consistent and understandable. The internal CGEvent/AppKit/HID numbering may differ; normalize and document mapping rather than assuming all APIs use the same index base.

**Acceptance M1:** In actual hardware testing, distinguish Button 4 from `Control + Button 4` while preserving the unmapped plain button behavior.  
**Acceptance M2:** When an additional button is observable beyond Button 5, the recorder captures it and the system can bind it without an enum change.

### 3.3 Manual profiles and category-wide rule scoping (CORE)

Rules are category-wide within one manually selected profile. Device inventory and mouse-specific settings (§3.2) do not scope rules to a physical device or switch profiles automatically. The withdrawn rule-attribution experiment is historical; it is not evidence that macOS cannot enumerate devices.

- A profile is a named, local set of rules for every supported input category. Exactly one profile is selected; the engine evaluates only its enabled rules.
- Create an empty profile, duplicate rules with new binding IDs, rename and delete profiles with confirmation; keep at least one. Names are unique without case/accent differences, 1–80 characters, no control characters. Bound the configuration to 20 profiles and 1000 total rules.
- Switch manually from the main window or Menu Bar menu with the current selection clearly indicated. Profiles are independent of mouse connection, receiver presence, applications and workspaces.
- Category-wide rules cover Keyboard, Mouse, built-in Trackpad, external Magic Trackpad and the separately research-gated Magic Mouse. A profile named after a mouse still applies to every connected mouse; names are labels, not device IDs.
- Preserve the global pause state when selecting, creating or deleting a profile. Persist profiles and selection locally. Legacy configuration migrates rules, IDs, actions, flags and timings into a default profile without rewriting until a successful save.
- Switching cancels recorders, pending output, double-press/hold/pointer recognition. Keep ownership of already suppressed presses until release to preserve down/up symmetry. A stale editor cannot save into a newly selected profile.
- On validation or disk-write failure retain the prior selection/configuration/runtime. Unreadable or incompatible files lock editing; never silently overwrite them.
- No physical-device selector/scope, private sender API or automatic device-driven activation for rules/profiles. Settings → Devices inventory and mouse-specific preferences remain separate; ordinary safe mouse diagnostics stays available.

**Acceptance D1:** Disconnecting hardware does not erase any profile or its rules.

**Acceptance D2:** Manually selecting a profile applies only its rules, preserves pause, survives reload and safely cancels the previous recognition/recording state. Physical-device precision is withdrawn by this decision.

### 3.4 Built-in trackpad and Magic Trackpad (RESEARCH-GATED)

Use the same curated preset pool for the built-in trackpad and any connected external trackpad-shaped surface. They are separate input categories with independent rules; the external category is not a selector for a particular physical device.

- Single tap with 3 or 4 fingers, without pressing the trackpad.
- Double tap with 2, 3 or 4 fingers. A lone two-finger tap has no rule fallback; delay a single only when a corresponding double-tap rule needs disambiguation.
- Physical click with 2, 3 or 4 contacts. Contact count or a pressure threshold alone does not prove a click; two fingers count only when macOS reports the secondary button. A configured click rule replaces that click.
- One-finger tap in each of the four corners. With Tap to click enabled, consume the click synthesized from a configured corner tap so the rule replaces it.
- One optional held Command, Option, Control or Shift chosen from a fixed list beside the preset. Match exactly; the same preset with and without that key can have independent rules. Multi-modifier chords are unavailable.
- Safe movement/duration/corner tolerances, debounce, click exclusion and cancellation. Expose advanced tuning only where necessary.

Present one selector of complete gestures, such as `Double tap · 3 fingers` or `Top-left corner tap`, followed by the shared action catalog and its parameters. Finger count, click/tap kind and corner belong to each preset: no separate controls or touch trigger recorder. Output-shortcut recording stays independent.

General one/two-finger single taps, five-finger gestures, holds, swipes (including diagonals), pinch, rotation and Force Click are outside this scope. Leave unmatched scrolling and system navigation intact. Magic Mouse has its own research gate (§3.5).

Raw contact observation does not establish native gesture suppression. Apart from the configured click/corner replacement above, preserve native gestures and disclose possible double effects. Verify Look Up/data detectors, Smart Zoom, secondary click, Mission Control, Spaces, scrolling, App Exposé and relevant system settings. Never label a rule a clean replacement without evidence.

[CAPABILITIES](CAPABILITIES.md) and [trackpad tasks](tasks/README.md) own implemented subsets, dated software/hardware results and remaining timing, coexistence, recovery and platform acceptance. They do not expand release support through compilation alone.

**Acceptance T1:** On tested physical trackpad hardware, a four-finger tap can generate one `Command + W` in a supported setup, without unsafe duplicate behavior.  
**Acceptance T2:** Gesture classification is debounced, produces no accidental extra actions, and respects user pause.

### 3.5 Magic Mouse (RESEARCH-GATED)

Treat Magic Mouse as a dedicated surface device, **not merely a two-button mouse**. Investigate observable touch points and firmware/OS constraints. Desired gestures include:

- Normal primary/secondary clicks, scrolling and horizontal scrolling.
- One- and two-finger tap/swipe behaviors when raw touch data is accessible.
- Holds and directional swipes; combinations with keyboard modifiers.
- Device-specific supported gestures; do not assume three/four-finger Magic Mouse interactions equivalent to trackpad.
- Correct coexistence with native Magic Mouse scrolling/navigation and gesture suppression limits.

Prefer sharing recognition logic with trackpad when contact data semantics match; use a dedicated acquisition adapter when they do not.

Use the same preset-only editor contract as Trackpad: one Magic Mouse-specific
gesture selector and the shared action selector. Each preset contains its complete
finger count/direction/hold semantics. No touch trigger recorder or separate
gesture-type/finger/direction controls. Curate the release pool against native
macOS reservations and actual hardware evidence; never infer the pool from
Trackpad or expose arbitrary gesture construction.

**Acceptance G1:** Only gestures verified on a real Magic Mouse are marked supported.  
**Acceptance G2:** Device disconnect/reconnect and gesture cancellation do not leave stuck input states.

## 4. Recording and editing rules (CORE)

Provide a clear **Add Binding** flow:

1. Select a profile and input category.
2. For Keyboard or conventional Mouse, click **Record Trigger**; show a distinct listening state and Escape/cancel control. For Trackpad or Magic Mouse, choose one complete gesture from the predefined category-specific selector.
3. Capture key + modifiers or extra mouse button where recording applies; show a human-readable summary. Touch preset selection is immediate and does not execute an action.
4. Choose from searchable, categorized actions or record an output keyboard shortcut.
5. Adjust relevant options, review conflicts, and save.

Requirements:

- The entire Trackpad selector (label, empty space and chevrons) opens its curated presets directly, without an intervening category submenu.
- Differentiate trigger recorder from output shortcut recorder. Do not accidentally execute output during recording.
- Touch input exposes only the curated gesture pool. Output keyboard-shortcut recording remains available to every category and is independent of trigger selection.
- Always provide cancel/retry/clear; scope recording to the active prompt; suppress or neutralize recorded events only when safe and possible.
- Avoid capturing keys used to dismiss the recorder without explicit handling.
- Show disabled/unavailable input modes with explanations, not a fake gesture recorder.
- Edit, delete, duplicate, enable/disable individual rules and copy a rule to another profile; a copy whose trigger is already used there arrives switched off. A rule may carry a short note (up to 80 characters) shown in the list and matched by search. Show clear trigger→action in the bindings list.
- Conflict handling is deterministic; duplicate bindings should not be silently accepted.

**Acceptance R1:** A nontechnical user can create `Control + Mouse Button 4` → `Command + W` without entering a key code or mouse index.

## 5. Action catalog (CORE, availability-gated)

Every supported trigger uses the **same** action catalog. Group actions, search them, and expose parameters only when the chosen action needs them.

### Keyboard and mouse output

- Send key or keyboard shortcut with correct down/up order.
- Restore/release synthetic modifier states after cancellation/error.
- Mouse left/right/middle click, double click, back/forward equivalent when safe, and scroll output where feasible.
- Named standard commands (Copy, Paste, Cut, Undo, Redo, Select All, tab and zoom commands, screenshots) are fixed shortcuts with their own catalog entries; the editor states which shortcut is sent.
- Insert Text types user-authored text (1–500 characters, no control characters, at most 10,000 UTF-16 units) into the app in front. The additional encoding bound limits unusually long combining sequences; the editor explains a rejected overlong encoding. It is stored locally without encryption and the editor says so.
- Do Nothing swallows its trigger. Pause Rebind, Next Profile and Previous Profile control Rebind itself; resuming is only possible from the menu or window because rules do not run while paused.

### Windows and applications

- Close active window (`Command + W` where appropriate), minimize, hide application, toggle full screen; App Exposé, Mission Control, Show Desktop.
- Window tiling/resizing/moving using suitable macOS API or Accessibility, **only when the app/window supports it**: halves, quarters, fill, center and move to the next display.
- Switch windows/apps; open/activate/quit a specified app; open URL/file; run an Apple Shortcut where a reliable integration exists.

### Spaces and system

- Next/previous desktop or Space via validated user-configured system shortcut or another proven method; macOS has no guarantee of a single documented universal 'move Space' API. Detect or explain shortcut dependencies.
- Previous/next Space must behave like the native Control + Left/Right Arrow action: normal system transition (respecting Reduce Motion), display selection and first/last-Space boundaries. Do not substitute instant switching or a fling past the final desktop that produces a black screen and returns. Hardware acceptance must cover both animation and boundaries (user clarification, 2026-10-09).
- Audio volume up/down/mute; play/pause/next/previous track when available.
- Lock screen; sleep; open System Settings; display brightness only if hardware/OS provides an appropriate method.
- Launchpad only if a currently supported and robust mechanism exists. Do not pretend a removed or private OS behavior is universal.

### Advanced, optional after core

- Explicit user-defined AppleScript/shell command. Never run arbitrary untrusted shell snippets or interpolate raw event content into shell commands. Document permission and execution behavior; keep disabled unless configured.

**Action status:** An item appears as `available` only if implemented for the current system. Unsupported or permission-dependent actions should be hidden or clearly explained, not selectable as inert entries. Prefer dedicated system APIs; if a shortcut is used as implementation, describe its reliance on macOS shortcut settings.

**Acceptance A1:** Every advertised action has a real execution path and an error/reporting strategy.  
**Acceptance A2:** Synthesized actions cannot feed back into their own triggers indefinitely.

## 6. Global input runtime and safety (CORE)

Potential ingredients (choose on evidence, not by fiat): Quartz `CGEventTap` for supported global intercept/suppression, HID/IOKit for low-level data and enumeration, AppKit for app-level events, Accessibility for certain target actions, and private MultitouchSupport only if required and acceptable.

Required runtime behavior:

- Start engine after necessary permissions are available; do not block the main window or first-run onboarding.
- Process global events while the app window is closed.
- Never depend on a SwiftUI view staying alive for global interception.
- Account for event-tap timeouts/disable notifications, sleep/wake, fast user switching as applicable, system lock/unlock, device loss, and revoked permissions.
- Fail open on invalid rules and unexpected errors. Pausing/disabling must restore passthrough and release synthetic states.
- Do not perform blocking UI/persistence/script work on the event callback thread. Record only safe metadata in diagnostic mode, and bound log volume.
- Avoid collecting key content, password input, or clipboard data; no background surveillance, network calls, or telemetry.
- Prevent unsafe remappings from causing inaccessible controls. Provide a visible Menu Bar emergency disable; evaluate an optional emergency key combo that cannot itself be swallowed by a custom rule.
- Sensitive OS contexts may forbid input injection or interception. Treat these cases honestly.

**Acceptance S1:** With remapping disabled, normal keyboard and mouse behavior is restored immediately.  
**Acceptance S2:** Missing required Accessibility/event-posting access is displayed and explained, not silently worked around. Input Monitoring is shown as not required for the current active Quartz tap.
**Acceptance S3:** No raw typed text is persisted or logged.

## 7. Permissions and onboarding (CORE)

- Show first-launch guidance for actual Accessibility and event-posting checks. Input Monitoring is not a startup gate for the current active Quartz tap; Automation remains action-specific. Optional Bluetooth battery access is requested explicitly in Devices (§3.2) and does not gate normal input rules.
- Check actual state using the best available public APIs for the capture/dispatch method. macOS permission UI and state are not always perfectly synchronized; do not treat button taps as proof of authorization.
- Buttons to open the right System Settings pane; re-check after return, focus, or explicit Refresh.
- Give helpful errors for failure to create an event tap and permission changes.
- Do not request Full Disk Access, Screen Recording, root privileges, or system protection changes for an unrelated function.
- Document code signing/bundle ID considerations if permissions reset between Xcode builds.

## 8. Background behavior (CORE)

- Menu Bar menu: Open Rebind, select active Profile, Enable/Disable Bindings, Settings, Quit; status/permission hint when relevant.
- Closing the window **does not quit** the remapping engine; a user-configurable menu-bar-only experience is welcome if straightforward.
- **Launch at Login** using ServiceManagement (`SMAppService`) where appropriate; show real state and errors.
- Avoid duplicate engine instances when reopening the window or relaunching.
- Remapping should resume after restart/login if enabled and allowed by OS permissions.

## 9. Persistence (CORE)

- Local-only versioned `Codable` configuration stored in the application support area, written atomically.
- Stable profile/binding identifiers, selected profile, names, category scopes, trigger parameters, action parameters, enabled flags, relevant gesture thresholds, app preferences, and schema version.
- Migration path for schema changes; reasonable recovery/backup behavior for corrupt or incompatible data; no silent erasure.
- Import and export user settings with validation and confirmation before destructive replacement.
- Export one profile to a file and import profiles from a file (2026-10-13). An import only adds profiles, with fresh identifiers and unused names; it replaces nothing and carries no app preferences or excluded apps.
- No SwiftData/SQLite/Core Data unless actual requirements demonstrate a need.
- Never store unstable HID pointers or raw platform objects as persistent identifiers.

## 10. Interface and design (CORE)

### Presence (2026-10-13)

General settings let the user hide the Dock icon, hide the Menu Bar icon and start without opening the window (including at login). With the Dock icon hidden, Rebind still appears in the Dock while one of its windows is open and leaves it when the last window closes; it keeps running until quit from the menu or with Command-Q. With both icons hidden, opening Rebind again shows its window. Rebind's windows open on the Space the user is on rather than switching back to the Space where they were first shown.

### Information architecture

Use a compact macOS desktop layout, preferably `NavigationSplitView`:

```text
Sidebar                          Main detail
-------------------------------- ------------------------------
DEVICES                          Keyboard / Mouse / Trackpad
  Keyboard                       Bindings list
  Mouse         Trigger → Action   Enabled
  Trackpad / Magic Trackpad      ...
  Magic Mouse                    [+ Add Binding]

--------------------------------
  Settings
  About
```

The sidebar lists input categories. Keep Settings and About visibly separated near the bottom. Put a compact profile picker and management button above the rules; no separate Profiles/Workflows/Actions navigation.

### Key screens

- Main bindings list with clear labels for trigger/modifiers/action, toggle, edit, delete, empty states, Add Binding.
- Create/edit binding sheet or equivalent focused flow; searchable action picker, capture UX, conditional options, conflict messages.
- Settings: General (launch at login, background/menu bar behavior, global enabled), Permissions (status, refresh, open settings), Input (mouse gesture distance, vertical and horizontal wheel direction, wheel speed, excluded apps with separate Bindings and Smooth scrolling switches), Devices (local device names, discovered keyboards/battery devices, per-mouse smooth scrolling, Logitech hardware settings, battery and gesture button, §3.2), Language (System, EN, RU, DE, FR, ES, Simplified Chinese), Advanced (diagnostic event viewer showing safe metadata, a support report without binding content, import/export/reset).
- About: icon, Rebind name/version, brief description, credits/licenses, relevant links where available.
- First-run permissions onboarding with accurate statuses.

### Visual language

- Design for **macOS 26+** with a distinctive, calm and soft native appearance (user decision 2026-10-12, superseding the earlier Liquid Glass direction): opaque-first raised surfaces, soft shadows and hairlines, capsule controls, raised keycaps as the brand motif and one accent color, with excellent typography, alignment, spacing, hierarchy and contrast. No Liquid Glass. Native controls retain their semantics while adopting the design-system tokens.
- Only the sidebar and menus may use a system material. Follow [DESIGN](DESIGN.md) and the current Sketch variables/styles/components; preserve opaque Reduce Transparency fallbacks.
- Distinct, readable panes; avoid stacked translucency and giant decorative cards.
- Native button/menu/focus semantics; SF Symbols; polished hover/focus/pressed states.
- Support Light/Dark, window resizing, accessibility, Reduce Transparency, Reduce Motion, Increase Contrast, VoiceOver, full keyboard operation.
- Inspect the relevant current Sketch frames, components/styles and screenshots via MCP. Use the user-identified design as visual direction while preserving native macOS behavior. Exported images do not replace the live design; if access or the target is missing, explain the limitation and request the document/frame.
- **No generic AI slop:** no gratuitous purple gradients, blur effects, massive corner radii, fake analytics dashboards, or unrelated micro-illustrations.

### Application icon

Use the current Sketch brand: a full-bleed blue keycap with two opposing white arrows, legible at small sizes and without text. Deliver the native Icon Composer asset and inspect its built Dock/Finder artwork; [DESIGN](DESIGN.md#brand) owns the source and delivery paths. System rendering supplies the final corner mask and lighting.

### Menu Bar icon

Provide a separate monochrome vector template derived from Rebind's brand mark, with transparent background and open counters at menu-bar size. macOS supplies the foreground color for light/dark and selected states; do not shrink the decorated Dock icon or bake a background, lighting, or shadow into this asset. A second template with pause bars is shown whenever rules cannot run (paused, missing permission or locked storage). Keep the accessible app name and display runtime/permission/pause status in the menu, with emergency pause always reachable (§§6, 8).

## 11. Localization (CORE)

- App languages: **English**, **Russian**, **German**, **French**, **Spanish** and **Simplified Chinese** (the last two added 2026-10-13 by user request). Select system-preferred supported locale by default; English fallback.
- Manual language selection includes **System Default** and each language's autonym. Selection edits a draft; Apply appears only when it differs from the saved preference. Leaving without Apply discards the draft.
- Apply saves atomically while preserving profiles, rules, pause and every unrelated preference. A failure retains the draft for retry and leaves saved/active language unchanged; corrupt/future-file protection still applies.
- Saved preference and currently rendered language are distinct. Keep the complete UI in its active language until an ordinary user-controlled quit/reopen activates the saved choice; show clear reopen guidance. Never restart capture or quit/relaunch automatically as a language side effect. System Default resolves ordered supported system preferences on launch with English fallback; app-only Cocoa projection must agree with the stored choice and be repairable after interruption.
- Preserve user-entered profile/rule names, paths, action identity and shortcut glyphs. Translate the interface, not stored user content.
- Use String Catalogs; localize every visible label, action name, hint, onboarding message, error, About/Settings screen, and accessibility label.
- Localize keyboard/modifier display where appropriate without corrupting familiar macOS key glyphs (`⌘`, `⌥`, `⌃`, `⇧`).
- Test longer DE/FR strings and pluralized/error messages.

## 12. Reliability, performance, and testing

### Automated tests

- Binding matching and exact modifier semantics.
- Profile selection, independent rule sets, within-profile conflicts, safe switching, legacy migration and failed-save rollback.
- Key/mouse down/up lifecycle, holds/double taps, action-once policy, gesture recognition threshold/cancellation.
- Synthetic event filtering/feedback prevention; pause/fail-open behavior.
- Versioned JSON persistence, import/export, corrupt data recovery and migrations.
- Localization key completeness check where practical.

### Manual hardware and OS validation

Record tested macOS build, Mac model, input devices, relevant settings, permission status, and exact reproduction steps. Minimum real checks: conventional keyboard, a mouse with side buttons, MacBook or Magic Trackpad for four-finger tap, and Magic Mouse when available. If hardware is unavailable, status is **unverified**, not passed.

Check: click-through suppression, screen lock/unlock, login relaunch, window closed, app disabled, keyboard layout change, required permission revocation, manual profile changes while inputs are held, and OEM mouse driver interference.

### Build quality

- Clean Xcode build and meaningful core test results.
- No known crashes, stuck keys, event storms, or unbounded resource growth in ordinary use.
- No fake data or settings controls; incomplete features must be explicitly marked and isolated.
- Include basic developer launch instructions and notes for permissions/signing; no promise of notarization unless actually performed.

## 13. Capability status policy

Use this capability status vocabulary consistently in STATE, CAPABILITIES, verification records, PLAN and, when relevant, the UI. Task stages (design-ready, implementing, awaiting verification, etc.) are separate and defined in [WORKFLOW](WORKFLOW.md):

- `Planned`: no implementation yet.
- `Researching`: technical feasibility currently being established.
- `Implemented`: code path exists; may need physical verification.
- `Verified`: tested successfully on named real hardware/macOS build.
- `Experimental`: works only under stated conditions or may conflict with OS behavior.
- `Blocked`: specific measured platform/driver limitation.
- `Unsupported`: demonstrably unavailable in this architecture.

Compilation, screenshots, mocks, or a GitHub README **do not by themselves justify Verified**.

## 15. Product acceptance walkthroughs

A release candidate should explicitly evaluate and record all of these, with honest qualifiers where macOS prevents a full remap:

1. Record mouse Button 4; map `Control + Button 4` to Next Desktop; plain Button 4 retains original behavior.
2. Record `Control + Option + Button 5` to output `Command + Shift + T` without modifier leakage.
3. Remap a keyboard physical key to a different key/shortcut, across supported layouts and app focus changes.
4. Connect mouse with additional OS-observable buttons beyond Button 5 and bind any observable one.
5. Hold Button 4 + move left to perform exactly one chosen action.
6. Choose the four-finger tap preset and trigger `Command + W` on compatible hardware without unexplained double effects.
7. Select and use at least one predefined genuine Magic Mouse touch gesture on real hardware; document capture/coexistence evidence and any tested blocker before release.
8. Close Rebind's window and continue running via Menu Bar.
9. Restart/login, reload rules and enable state, respecting actual permissions.
10. Remove permissions or toggle Pause; keyboard/mouse continue to work normally.
11. Choose each of EN/RU/DE/FR/ES/Simplified Chinese, open every primary screen, and verify no broken layout/untranslated core UI.
12. Export bindings, reset, import, and observe restored behavior.

## 16. Definition of Done

Rebind is **not done** merely because it has a beautiful SwiftUI UI, compiles, or passes isolated matcher tests. Done means the tested and claimed triggers run their actions in real applications, input remains safe, background/permissions work, settings persist, and the interface and translations are finished. Anything not hardware-verified must carry an accurate capability label and a corresponding capability/task verification entry, indexed by STATE and the relevant PLAN phase. Keep requirements here and dated implementation evidence in their owning records.
