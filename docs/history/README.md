# Project history

History records dated outcomes and reasons. It is not startup instructions or a list of currently supported capabilities. Read [STATE](../STATE.md), [PLAN](../PLAN.md), the affected task and current source first.

- [2026-10](2026-10.md): new concise entries after workflow migration.
- [Implementation through 2026-10-10](implementation-through-2026-10-10.md): concise technical outcomes, earlier research decisions and scoped software/manual evidence. Earlier failed/removed approaches remain identified as superseded; new decisions belong in current tasks/research.

Raw migration snapshots and workstation access hints were never versioned (the local `.local/agent-context/` folder that held them was retired on 2026-10-13). They are not part of published history and are not required to continue development. Git history and the current technical records preserve project context.

For each substantive session append a short entry to `YYYY-MM.md` (newest first): date, task/outcome, reason or changed decision, evidence link, unresolved check/next action. Link to task/verification detail instead of repeating tool transcripts. Multiple sessions on a date can have descriptive headings. Preserve others' entries when updating the shared month file.

Keep durable technical facts/results in the repository, written in English. Summarize a reported test result with date, scope and limits; do not quote the person's reply. Temporary logs/screenshots may disappear; their presence is not necessary for a future agent to understand the recorded result. Keep chat/tool transcripts, personal paths, typed input, secrets and actual user configurations out of published history.
