## Outcome and scope

User simplification, 2026-10-27: use one Color well for the entire keyboard; independent key/logo colors are out of scope. The user subsequently authorizes finishing and packaging the software while the keyboard is disconnected, with physical acceptance deferred. Implementation is limited to the measured G915 TKL LIGHTSPEED family; other keyboards keep their existing cards until their brightness/zone behavior is established.

For a Logitech keyboard that reports HID++ lighting, Settings → Devices lets the user turn the backlight on/off, set its brightness and pick one shared static color for all supported zones (keys and logo). An optional low-battery mode (Keep color / Red / Blinking red) turns the lighting red below 10 % while not charging and restores the saved color after charging. While G HUB runs, lighting controls are disabled behind the existing companion-app banner pattern.

Idle timeout (user addition 2026-10-26): add **Turn off when idle** using the keyboard’s native inactivity/power-mode configuration. Proposed presets: Device default, 30 seconds, 1/2/5/10 minutes, Never. Initial Device default does not write; returning to it restores the captured native policy. Show only confirmed supported options, preserve a current custom value, and omit the row on unsupported hardware. Never needs confirmed firmware semantics. Idle-off takes precedence over low-battery colors; battery refresh must not wake the lighting. No host keyboard-content collection, global activity monitor or periodic idle polling.

Out of scope (user decision 2026-10-24: drop anything complex or unclear): per-key colors (0x8081), animated effects (wave, ripple, cycle), lighting actions in rules, non-Logitech lighting, OpenRGB/Solaar code (GPL; Rebind is MIT, protocol facts only).

## Hardware facts (read-only probe, agent-observed 2026-10-24)

G915 TKL on Lightspeed receiver `046d:c545`, slot 1, macOS 27.0.1. A local read-only HID++ 2.0 probe (feature set enumeration and `getInfo`/`get` calls only, no writes) found 0x8040 Brightness Control (max 100, 5 steps, current 50), 0x8071 RGB Effects and 0x8081 Per-Key Lighting V2, plus 0x8100 Onboard Profiles. 0x8071 reports two zones: zone 0 location 0x0002 (logo) with Disabled/Static/Cycle/Breathing; zone 1 location 0x0001 (keys) with Disabled/Static/Breathing/Cycle/Wave/Ripple and an unidentified effect 0x0C. Static color and breathing color exist in both zones, which covers the scoped design. Probe source stayed in the session scratchpad and is not versioned.

Agent-observed results:

- 0x8071 index 0x0A: two zones (logo/keys), static effect ordinal 1 in both. Software ownership **0 → 1 → 0** acknowledged/read back; blue `20 80 FF` volatile effects acknowledged for both zones. The tester confirms both keys and logo visibly became blue on October 27. This device does not advertise stored-effect readback (extended capabilities 0x0004) or zone EEPROM persistence. No non-volatile effect, profile-mode or per-key write was attempted.
- Native policy initially flags 0, power-save 120 s, off 300 s. Off-only writes 30 s and 150 s preserved flags/dimming and read back; sampled modes were FullRGB at 40 s and PowerSave at 165 s, respectively. No controlled tester inactivity interval was supplied, so these are not timing failures or proof of timeout semantics.
- A bounded diagnostic temporarily set power-save/off to **5/15 s**, retaining flags; ownership 1 and activity-event request flags 6. At 25 s, `get_power_mode` reported **3 (PowerOff)**, and still 3 ten seconds later. No host off command/timer was used. This establishes native off can occur while software controls static zones; it does not establish exact timeout origin, activity wake, Never encoding or color persistence. No activity notifications were received in this interval.
- Every completed write trial acknowledged restoration and read back **brightness 50, native policy flags 0 / 120 / 300 s, ownership 0 / event flags 0**. Returning firmware ownership is confirmed by protocol; restoration of visible onboard colors is not visually confirmed.

Visual retry on the same date: both zones acknowledged blue `20 80 FF` at brightness 50 for a two-minute observation window; initial power mode was FullRGB. Native policy remained unchanged throughout. At the end, brightness 50, policy 0 / 120 / 300 s and firmware ownership/event flags 0 were read back. The tester subsequently confirmed visible blue on both zones. Earlier trials received no visual observation and therefore establish protocol results only. This does not establish wake/reconnect/power-cycle or visible onboard-color restoration.

The initial read-only attempt reused software ID 8 and a short first-request timeout: one timed-out root response appeared against a later feature lookup. ## Implementation and verification — 2026-10-27

**1.0.0 (21), schema 46** implements the measured G915 TKL LIGHTSPEED subset in Settings → Devices: on/off, brightness and one shared static color, plus Keep color / Red / Blinking red for low battery. Firmware identity, 0x8040 range/step information and complete 0x8071 static-zone support gate exposure. No onboard-profile, EEPROM, per-key, rule or permission change. Other keyboard models are not admitted from feature presence alone.

The brightness probe found that requests are quantized: 13 → 12, 37 → 25 and 75 → 50, despite acknowledgements. Native **12/25/50/100** read back exactly; zero is the separate switch. Only those levels are selectable/storable. The first arbitrary-value diagnostic failed readback and restored brightness 50; this is why a continuous percentage range was removed.

The new app driver was exercised outside the app on G915: static blue, brightness 50 → 0 → 50 and original firmware ownership/brightness restoration acknowledged/read back. After a temporary native 5/15 s policy reached PowerOff, a plain brightness write did not wake lighting. A short, explicit power-control lease plus `setPowerMode(1)`, immediately returning the original control flags, recovered FullRGB. This fixed path was hardware-observed; policy 120/300 s remained unchanged after restoration. Physical Shift wake and receiver/power-cycle recovery remain unverified. The low-battery diagnostic used an injected 8% status (not a real battery transition): native breathing-red writes and brightness 25 acknowledged; its initial 37% recovery target was quantized and rejected. The corrected four-step recovery is software-tested; visible blinking/real charge recovery still needs hardware observation.

All HID I/O stays on the existing endpoint queue. Rapid color-panel changes coalesce, stale/revoked writes cannot persist, and rejected writes retain the previous saved preference. Connection-scoped ownership survives adapter refresh, records cleanup obligations even after a lost acknowledgement and releases on orderly quit. Battery refresh changes output only while native lighting is active; unknown charge does not undo an existing low-battery override. Existing receiver reconnection and macOS wake notifications revalidate stored settings. No host idle polling, key-content collection or new background timer. G HUB/companion exclusion uses the existing detector and per-transaction access revisions; actual concurrent-helper timing remains a hardware check.

Configuration 46 stores model-keyed lighting preferences separately from rules/profiles, migrates 1–45 without inventing lighting choices, and rejects duplicates, unsupported levels and newer payloads under old schema versions. AppModel persists only acknowledged operations. Identical models share preferences. The color well proposes an initial color until one is chosen: this firmware cannot read the current onboard effect. Native ColorPicker supplies the well/panel without alpha; copy says “Choose one color…” rather than implying an onboard-color read. Slider accessibility values include their displayed units. The native timer row is **not exposed**: ordinary native idle policy is untouched; exact preset/Never semantics remain unconfirmed. This is an explicit remaining requirement, not a host-timer substitute.
